## 二、最有价值的发现：度量能力立刻推翻了一个错误判断

### 经过

我先实现了混合检索（向量 + BM25 + RRF 融合），主观判断「这是业界公认的最佳实践，必然是提升」。

**然后我建了黄金测试集并跑了对照实验，结果是被打脸的：**

| 指标 | 向量-only（基线） | 混合检索（初版） | 结论 |
|------|------------------|-----------------|------|
| Hit@5 | 83.3% | **80.0%** | ❌ 退步 3.3 个百分点 |
| Recall@5 | 78.9% | **75.6%** | ❌ 退步 3.3 个百分点 |
| MRR | 0.757 | **0.728** | ❌ 退步 |

**如果没有这套评估，我会把一个退步当成改进交付出去。**

### 定位根因

分析发现：中文按**单字**切分做 BM25，会让「的 / 了 / 是」这类高频字到处命中，
BM25 分数被噪声淹没，融合时反而把好的向量候选挤出了 Top-K。

### 修复与验证

把中文切分改为**二元组（bigram）**——保留词序信息、区分度显著更高：

| 指标 | 向量-only | 混合（单字） | 混合（bigram 修复后） |
|------|----------|-------------|---------------------|
| Hit@5 | 83.3% | 80.0% | **83.3%**（持平） |
| Recall@5 | 78.9% | 75.6% | 77.8% |
| MRR | 0.757 | 0.728 | **0.758** |
| **keyword 类 MRR** | 0.783 | — | **0.917** ⬆️ |
| 平均检索耗时 | 182ms | 30ms | **34ms** |

**结论（如实陈述）**：混合检索在**目标场景（错误码/型号类 keyword 查询）明显提升**
（MRR 0.783 → 0.917），整体指标持平，延迟反而下降。
它不是「全面提升」，而是「用中性代价换取目标场景的显著收益」——这个判断只有靠数据才能做出。

## 三、评估体系

### 黄金测试集（`eval/golden_set.json`）

30 条，覆盖四类：

| 类型 | 数量 | 考察点 |
|------|------|--------|
| fact | 13 | 事实型检索准确性 |
| keyword | 6 | **错误码/型号类**（混合检索的目标场景） |
| multihop | 6 | 跨文档综合能力 |
| refusal | 5 | **知识库无答案时的拒答能力** |

### 指标

- **Hit@K**：期望文档是否出现在 Top-K
- **Recall@K**：期望文档被召回的比例
- **MRR**：第一个命中文档的排名倒数
- **拒答正确率**：无答案时最高相似度是否低于阈值

### 用法

```bash
cd eval
python run_eval.py            # 自动对比 向量-only vs 混合检索
python run_eval.py --config hybrid
```

## 四、被证明无法用当前手段解决的问题（如实记录）

### 拒答阈值失效 —— 且无法用单一阈值解决

测试集专门放了 5 个「知识库无答案」的问题。实测数据：

| 类别 | Top1 相似度范围 |
|------|----------------|
| 可回答问题 | 0.4354 ~ 0.7023 |
| 拒答问题 | 0.3723 ~ **0.7045** |

**两类分数完全重叠**——`r04`（问 Python SDK，知识库无此内容）的相似度 0.7045，
比很多合法问题的分数还高。**任何单一绝对阈值都无法分开二者。**

**为什么**：BGE-small 这类 bi-encoder 的余弦相似度衡量的是「语义大致相近」，
对「主题相关但无答案」的问题天然会给出较高分。

**业界解法**（本环境无法实施，因 HuggingFace 被网络阻断）：
1. **引入 Cross-encoder Reranker**（BGE-reranker）——对 query+chunk 联合打分，精度显著更高
2. **LLM-as-Judge 做相关性判定**——额外一次 LLM 调用
3. 换用更强的 embedding 模型

**当前的实际表现**：检索层的阈值过滤确实失效，但**生成层的拒答是有效的**——
System Prompt 明确要求「知识库未收录时诚实说明」，实测该路径工作正常。
即：阈值是粗过滤，真正的拒答保障来自 Prompt 约束。

> 这是一个**诚实的局限声明**，也是下一步最明确的优化方向。

## 五、新增能力的技术细节

### 1. 缓存失效修复

`utils/cache.py` 增加**失效回调注册机制**：

```python
register_invalidation_hook(fn)   # 语料变更时一并执行
clear_cache()                    # 清空检索缓存 + 触发所有 hook
```

rag_service 在 import 时注册 `clear_bm25_cache`，避免 utils 层反向依赖 services 层的循环导入。

**修复效果**：文档删除/重建后，检索缓存与 BM25 索引**同时失效**，
用户不再会看到引用已删除文档的答案。

### 2. 阻塞事件循环修复

```python
context, sources, trace = await asyncio.to_thread(
    search_knowledge, data.query, RETRIEVAL_TOP_K, collection_names
)
```

embedding 是同步阻塞的 CPU/GPU 操作，直接放在 `async` 函数里会卡住整个事件循环。
同时注意：**不能把 db session 传进线程**（SQLAlchemy Session 非线程安全），
因此只把纯计算的检索逻辑放进线程池。

### 3. 检索日志（可观测性）

新增 `retrieval_logs` 表，记录每次检索的：

- 两路召回的**各自候选集**（`vector_hits` / `bm25_hits`）
- RRF 融合后的候选数、去冗余剔除数
- 最终入选的 chunk ID、检索耗时

**它回答了一个关键问题**：用户点踩时，「到底是没检索到，还是检索到了但模型没用？」
——没有这张表，这个问题只能靠猜。

新增 `GET /api/knowledge/retrieval-stats` 统计两路召回的贡献占比。

### 4. 用户反馈闭环

- `messages` 表增加 `feedback / feedback_reason / feedback_comment / feedback_at / retrieval_log_id`
- `POST /api/chat/messages/{id}/feedback` —— 点赞/点踩 + 原因标签
- `GET /api/knowledge/bad-cases` —— bad case 归档，**每条附带当次检索明细**
- 前端：答案下方 👍/👎 按钮，点踩时弹出原因标签（不准确/不完整/过时/无关）
- SSE `done` 事件新增 `message_id`，使前端能关联到真实消息记录

**闭环意义**：`反馈 → 检索日志 → 定位根因 → 补知识库/改检索 → 加入黄金测试集防回归`。

### 5. 配置路径健壮性

**发现的隐蔽缺陷**：`CHROMA_PERSIST_DIR=./chroma_data` 是相对路径，按**工作目录**解析。
从别的目录启动时，会静默连到一个**空的数据目录**——表现为「知识库明明有数据却检索不到」，
且不报任何错。我在从 `eval/` 目录运行评估脚本时踩到了这个坑（检索全部返回空）。

**修复**：配置以 `backend/` 目录为锚点解析，从任意目录启动都读到同一份数据。

```python
BACKEND_DIR = Path(__file__).resolve().parent.parent
def resolve_path(p): 
    return str(p if Path(p).is_absolute() else BACKEND_DIR / p)
```
