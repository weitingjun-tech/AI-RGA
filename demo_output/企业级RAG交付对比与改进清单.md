# 企业级 RAG 交付标准 vs 本系统 — 对比与改进清单

> 目的：对照业界**真正交付上线**的 RAG 系统，找出本系统的差距并排定改进优先级。
> 结论先行：本系统是一份**质量不错的演示级实现**，功能面齐全；差距不在功能列表，而在
> **「度量能力」（评估 + 可观测 + 反馈）与「检索质量」（混合检索 + 重排）**两块。

---

## 〇、业界共识：RAG 的失败在哪里

调研多个生产案例后，三条共识：

1. **RAG 的错误 80% 发生在入库与检索层，不在 LLM。** 朴素流水线（切分→向量→TopK→LLM）在真实语料上召回失败率约 40%。
2. **收益最高的四件事按此顺序：分块 → 混合检索 → 重排序 → 查询改写。** 可叠加，跳过前面直接做后面收益会被抵消。
3. **评估体系不是一次性验收，而是持续基础设施。** 数据：94% 的生产团队有 tracing，但只有 52% 做离线评估、37% 做在线评估——**光有 trace 不会提升质量，必须闭环到评估**。

## 一、逐维度对比

图例：✅ 已具备　⚠️ 有但简化　❌ 缺失

### 1. 检索质量 — 差距最大的一环

| 能力 | 业界做法 | 本系统 | 差距说明 |
|------|----------|--------|----------|
| 向量检索 | BGE-M3 / text-embedding-3 | ✅ bge-small-zh-v1.5 | 模型偏小，但中文够用；选型是显存权衡，合理 |
| **混合检索** | 向量 + BM25，RRF 融合 | ❌ 纯向量 | **对型号/错误码/专有名词类 query 系统性失败**。而这类 query 恰恰是企业知识库最高频的 |
| **重排序** | Cross-encoder 精排 Top 20→5 | ❌ 无 | 业界实测 Top-5 相关性 60%→85%+，**单点收益最高** |
| **查询改写** | 多轮补全 / Multi-Query / HyDE | ❌ 无 | 多轮对话中「它多少钱？」无法补全为「CloudFlow 企业版多少钱」 |
| 父子分块 | 小分块检索、大分块喂 LLM | ❌ 单一粒度 | 检索精度与上下文完整性只能二选一 |
| 元数据过滤 | doc_type/dept/version 前置过滤 | ❌ 无 | 无法「只查某版本/某部门」 |
| 分块策略 | 结构感知切分 | ⚠️ 中文标点递归切分 | 已针对中文优化，比默认好；但未利用 Markdown 标题层级 |

> **实测佐证**：调研中的一个基准（1000 分块 / 100 query）：Dense-only Recall@5 = 0.71 → Hybrid(RRF) = 0.79 → 加 CrossEncoder 重排 = 0.84，MRR 0.58→0.73。延迟仅从 45ms 涨到 52ms。

### 2. 评估体系 — 完全空白

| 能力 | 本系统 |
|------|--------|
| 黄金测试集 | ❌ 无 |
| 检索指标（Recall@K / MRR / NDCG） | ❌ 无 |
| 生成指标（Faithfulness / Answer Relevancy） | ❌ 无 |
| 回归测试 / CI 门禁 | ❌ 无 |

**这是最致命的缺口**：没有它，**任何检索优化都无法验证是否真的变好**——只能凭感觉调参。它是做其他所有优化的**前置阻塞项**。

### 3. 文档处理流水线

| 能力 | 业界做法 | 本系统 |
|------|----------|--------|
| PDF 解析 | pdfplumber / Docling / MinerU（保表格结构） | ⚠️ PyPDFLoader（表格被拍平，扫描件解析为空） |
| OCR | Tesseract / PaddleOCR | ❌ 无 |
| 表格处理 | 表格作一等公民，转 Markdown 保结构 | ❌ 无 |
| 文件级去重 | SHA-256 | ✅ MD5（`get_file_hash`） |
| **分块级去重** | embedding 余弦 >0.7 判重 | ❌ 无（多版本重复入库会挤占 Top-K 名额） |
| **增量更新** | 只处理变更文件 | ❌ 无（每次全量重跑） |
| **文档版本管理** | version / effective_date / superseded_by | ❌ 无（过期制度文件与新版本一起被召回，合规风险） |
| Embedding 版本化 | 索引名带模型版本 | ❌ 无（换模型后新旧向量不可比，会静默产生垃圾召回） |

### 4. 生产化能力

| 能力 | 业界做法 | 本系统 |
|------|----------|--------|
| **异步任务队列** | Celery / ARQ / RQ | ❌ 裸 `threading.Thread(daemon=True)` |
| 任务重试 | 区分错误类型 + 退避 + 抖动 | ❌ 无 |
| 幂等 | Redis idempotency key | ❌ 无（重复上传重复入库） |
| 失败回收 | 超时任务进 DLQ | ❌ 无（进程重启后文档永久卡在 `processing`） |
| 限流 | 按用户 token bucket，跑到 80% 配额 | ❌ 无 |
| 成本控制 | 记录 token usage，按用户/小时看板 | ❌ 无（没有 token 台账 = 财务黑洞） |
| **并发控制** | Semaphore 限制 LLM 并发 | ❌ 无 |
| 缓存 | Redis + 语义缓存 | ⚠️ 进程内 LRU（见下方 bug） |

### 5. 多租户与权限

| 能力 | 业界做法 | 本系统 |
|------|----------|--------|
| 知识库级隔离 | 每租户独立 collection | ✅ 已实现（**索引级隔离，是正确且较强的模式**） |
| 文档级 ACL | chunk 带 access_level，检索时强制过滤 | ❌ 无（能访问某知识库即可检索其全部文档） |
| 租户上下文 | JWT 带 tenant_id → 注入向量查询 | ❌ 无 |
| 审计日志 | query + 召回 chunk + 权限判定，correlation ID 串联 | ❌ 无 |

> **关键原则**：权限必须在**检索查询层**强制生效，不能靠 Prompt 约束，也不能生成后再过滤（那时模型已经看过未授权内容了）。

### 6. 可观测性 — 基本空白

| 能力 | 本系统 |
|------|--------|
| 全链路 trace | ❌ 无（仅 8 处 `logger.` 调用） |
| 检索日志（候选集、分数、耗时） | ❌ 无 |
| 指标监控 / 告警 | ❌ 无 |
| 生产抽样评估 | ❌ 无 |

**检索日志的价值**：出问题时能回答「**这次答错，到底是没检索到，还是检索到了但模型没用**」——这是当前完全无法回答的问题。

### 7. 安全与护栏

| 能力 | 本系统 |
|------|--------|
| 输入注入检测 | ❌ 无 |
| **检索侧护栏** | ❌ 无 —— **知识库里放一份含「忽略以上指令」的文档即可劫持模型** |

## 二、审计中发现的真实 Bug（不只是「缺功能」）

### 🐞 Bug 1：检索缓存不会因文档变更失效 ⚠️ 用户可见

`utils/cache.py` 暴露了 `wrapper.cache_clear`，但 **`process_document` / `delete_document_from_chroma` / `reindex_document` 三处均未调用**。
**后果**：删除或重新索引文档后，最长 **5 分钟**内仍会命中旧缓存——用户会看到**引用已删除文档**的回答。

### 🐞 Bug 2：阻塞事件循环，并发能力差

`api/chat.py` 是 `async def send_message`，但内部直接调用 `search_knowledge()` → `embedding_model.embed_query()`，这是**同步阻塞**的 CPU/GPU 操作。
**后果**：检索期间整个事件循环被卡住，**并发请求只能排队**。用 `asyncio.to_thread` 包裹即可解决。

### 🐞 Bug 3：危险的「测试」脚本会清空知识库

`backend/test_rag.py` 开头即执行 `db.query(Document).delete()` ——**运行它会删除全部文档记录**。且它不是真正的测试（**零断言**、非 pytest）。
**后果**：误跑一次就清空知识库。

### 🐞 Bug 4：缓存为进程内状态，无法水平扩展

`_cache = LRUCache()` 是进程内 dict。uvicorn 多 worker 或 `docker-compose` 水平扩容后，各进程缓存互不可见——命中率被稀释，且行为不一致。

## 三、本系统的亮点（面试时应当主动讲）

客观地说，以下几处体现了超出「教学项目」的生产意识：

1. **多知识库按索引级隔离** —— 比业界常见的「共享索引 + metadata 过滤」更安全（后者一次漏加 filter 就跨租户泄露）。
2. **绕过 `ChatPromptTemplate` 直接构造 Message** —— 处理了知识库原文含 `{...}` 被误判为模板变量的真实边界问题。
3. **检索对单个集合做异常隔离** —— 某个库损坏不会导致整体检索失败。
4. **中文标点优化的递归分块** + 进程级 Embedding 单例懒加载。
5. **EPUB/MOBI 自研解析器** —— LangChain 生态无官方 Loader，属于生态缺口补齐。

## 四、改进优先级（按投入产出比）

排序逻辑：**先建立度量能力 → 再优化质量 → 最后补工程护栏**。
没有度量的优化是赌博；没有质量的基础设施是空转。

### P0 — 立刻做（收益最大、成本最低）

| # | 事项 | 为什么 | 复杂度 |
|---|------|--------|--------|
| 1 | **修复缓存失效 bug** | 真实用户可见 bug，改动约 5 行 | 极低 |
| 2 | **修复阻塞事件循环** | `asyncio.to_thread` 包裹检索，并发能力立刻改善 | 极低 |
| 3 | **修复危险测试脚本** | 移除 `delete()`，改为真断言或删除 | 极低 |
| 4 | **建黄金测试集 + 检索指标评估脚本** | **所有后续优化的前置条件**。50 条起步 | 中 |
| 5 | **接入 Rerank（BGE-reranker）** | 单点收益最高：Top-5 相关性 60%→85%+，约 30 行 | 低 |
| 6 | **用户反馈闭环**（点赞/点踩 + bad case 归档） | 成本极低，越早做积累样本越多 | 低 |
| 7 | **检索日志与 trace** | 排查「没检索到 vs 没用上」的唯一手段 | 低 |

### P1 — 1~2 个月

| # | 事项 | 为什么 |
|---|------|--------|
| 8 | 混合检索（BM25 + 向量 + RRF） | 解决型号/错误码类 query 的系统性失败 |
| 9 | 入库改造为任务队列 | 消除裸线程丢任务问题，获得重试/幂等 |
| 10 | chunk 元数据扩展 + 文档版本字段 | 为文档级 ACL 和「只召回最新版本」打地基，**越晚做重建索引代价越大** |
| 11 | CI 回归门禁（硬地板 + 漂移预算） | 把第 4 项从一次性变成持续 |
| 12 | Prompt 版本管理 | 极低成本换来灰度/回滚/归因 |
| 13 | token 计量 + 成本看板 | 财务依据 + 异常调用发现手段 |

### P2 — 3~6 个月

14. 父子分块（Small-to-Big）　15. 文档级 ACL + 租户隔离　16. 输入/检索侧护栏 + PII 脱敏
17. Redis 语义缓存（**必须做租户/版本命名空间**，否则是跨租户泄露）　18. 查询改写　19. PDF 解析升级（OCR + 表格）　20. A/B 测试平台

## 五、一句话总结

> 这个系统的差距**不在功能列表，而在「度量能力」和「检索质量」**。
> P0 的 7 项加起来能把它从「凭感觉调」推进到「有数据可依」——这是整个清单里回报率最高的部分。
