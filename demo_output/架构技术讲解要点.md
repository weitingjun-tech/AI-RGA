# RAG 知识库问答系统 — 架构技术讲解要点

> 用途：面试时应对「讲讲你这个项目的技术实现」以及深挖式追问。
> 原则：**先讲清一条完整链路，再讲关键决策的取舍，最后讲踩过的坑**——坑最能体现真实工程能力。

---

## 一、一句话说清项目

> 「这是一个企业级 RAG（检索增强生成）知识库问答系统：把企业散落的文档（PDF/Word/CSV/EPUB 等）灌进去，员工用自然语言提问，系统基于**文档原文**给出带**引用出处**的回答，从而显著降低大模型的幻觉。」

**核心链路**：文档上传 → 解析 → 分块 → 向量化 → 向量库存储 → 语义检索 → 拼装上下文 → LLM 生成 → 流式返回 + 来源标注

---

## 二、技术栈与选型理由

| 层 | 选型 | 为什么选它（面试要能说出理由） |
|----|------|------------------------------|
| 后端框架 | FastAPI | 原生 async + 自动生成 OpenAPI 文档；SSE 流式响应实现简单 |
| AI 编排 | LangChain | 统一的 Document 抽象和 Loader/Chain 接口，换模型/换向量库成本低 |
| LLM | Ollama + qwen2.5:7b | **本地私有化部署**，数据不出内网；企业知识库场景数据敏感，这是硬需求 |
| Embedding | BAAI/bge-small-zh-v1.5 | 中文语义检索效果优于通用多语言模型，且体积小、CPU 可跑 |
| 向量库 | ChromaDB | 轻量、嵌入式、免独立部署；支持持久化与 metadata 过滤 |
| 关系库 | MySQL | 存用户、会话、消息、文档元数据等结构化数据 |
| 前端 | React 18 + Vite + TS + Ant Design 5 | 类型安全 + 组件生态成熟，开发效率高 |

> **加分回答**：Embedding 模型选 `small` 而非 `large` 是**显存与成本的权衡**——本机 GPU 显存有限（GTX 1650），CPU 推理时 small 版本的延迟显著更低，而中文检索质量在知识库问答场景下差距可接受。这是「按场景选型」而非「无脑选最强」。

## 三、RAG 全链路技术细节

### 1. 文档解析（多格式支持）

通过 `LOADER_MAP` 做**扩展名 → 加载器**的注册表映射，新增格式只需注册一个类：

| 格式 | 加载器 | 说明 |
|------|--------|------|
| `.pdf` | PyPDFLoader | 逐页解析 |
| `.txt` / `.md` | TextLoader | 强制 UTF-8，规避 Windows GBK 问题 |
| `.csv` | CSVLoader | 每行一条 Document |
| `.docx` | Docx2txtLoader | 依赖 `docx2txt` 包 |
| `.epub` | 自研 EpubLoader | 基于 `ebooklib` 逐章节提取，BeautifulSoup 转纯文本 |
| `.mobi` | 自研 MobiLoader | 先用 `mobi` 包转 epub/html，再复用 epub 提取逻辑 |

> **亮点**：EPUB/MOBI 在 LangChain 生态里**没有官方 Loader**，是自己实现的——这属于「生态缺口补齐」，不是调包。

### 2. 分块策略（Chunking）

```python
RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
)
```

**关键点**：
- **分隔符针对中文优化**——按中文标点切分，避免把一句话拦腰截断
- **overlap=50** 保证跨块的语义连续性（一个概念被切开时，两块都还留有线索）
- **chunk_size=500** 是「检索精度」与「上下文完整性」的折中：块太大则检索不精准，太小则语义碎片化

### 3. 向量化与存储

- 用 BGE 模型把每个 chunk 编码成向量（`normalize_embeddings=True`，便于用余弦相似度）
- 存入 ChromaDB，**metadata 携带 `doc_id` / `doc_name` / `chunk_index`**——这是后续「引用溯源」和「按文档删除」的基础

### 4. 检索与阈值过滤

```python
score = 1.0 - distance          # 余弦距离转相似度
if score < RELEVANCE_THRESHOLD: # 默认 0.3
    continue                    # 过滤低相关片段
```

> **加分回答**：为什么要设阈值？因为向量检索**总会返回 top_k 个结果**，哪怕知识库里根本没有相关内容。不过滤的话，模型会拿着无关片段硬编答案——这正是 RAG 幻觉的常见来源。**阈值是幻觉控制的第一道闸门。**

### 5. 多知识库隔离（本次重点新增）

**问题**：所有文档混在一个集合里时，海量无关语料会「淹没」目标语料。
实测：知识库里混入一本 5250 分块的电子书后，问「版本更新内容」检索回的 5 条有 3 条是无关书籍，模型直接回答「未收录」。

**方案**：
- 新增 `knowledge_bases` 表，每个知识库绑定一个**独立的 ChromaDB collection**
- `documents.kb_id` 建立文档与知识库的归属
- 检索时把 `kb_ids` 解析成 collection 列表，**只在目标集合内检索**
- 支持多选：多库时各库分别检索，按距离升序**归并排序**后取 top_k

**效果**（同一问题的对照实验）：

| 检索范围 | 引用来源 | 回答 |
|----------|----------|------|
| 不限定（全库） | 3/5 是无关书籍 | ❌「知识库中未收录」 |
| 限定目标知识库 | 0/5 无关 | ✅ 准确列出全部更新内容 |

> **这是最能讲的一个点**：它体现了「**先量化问题、再设计方案、最后用对照实验验证**」的工程方法论。

### 6. 流式输出（SSE）

后端 `StreamingResponse` 逐块 yield，前端 `fetch` + `ReadableStream` 逐块渲染：

```
data: {"type":"chunk","content":"根据"}
data: {"type":"chunk","content":"知识库"}
data: {"type":"done","conversation_id":1,"sources":[...]}
```

**为什么重要**：LLM 生成慢，流式能把「首字延迟」从十几秒降到 1 秒内，用户体验是数量级的差异。`sources` 放在 `done` 事件里最后下发。

### 7. 性能与稳定性设计

| 机制 | 实现 | 解决的问题 |
|------|------|-----------|
| 检索缓存 | 自研 LRU + TTL 装饰器 | 相同问题重复检索直接命中内存 |
| Embedding 单例懒加载 | 模块级全局变量 | 避免每次请求重复加载模型（数百 MB） |
| 文档异步处理 | 上传后丢到后台线程 | 大文档不阻塞上传接口响应 |
| 连接池 | `pool_pre_ping=True` + `pool_recycle` | 避免 MySQL 长连接被服务端断开 |

## 四、踩过的坑（真实工程经验，面试加分项）

### 坑 1：SQLAlchemy Session 跨线程复用

**现象**：文档异步处理时报 `Packet sequence number wrong`。
**原因**：请求级的 `db` session 在请求结束后已关闭，后台线程复用它导致协议错乱；且 SQLAlchemy Session **非线程安全**。
**解决**：后台线程内创建**独立的 Session**，用完即关。
> 这体现对「Session 生命周期」和「线程安全」的真实理解，不是背概念。

### 坑 2：依赖缺失导致的功能静默失效

**现象**：`.docx` 上传后状态一直是 `error`。
**原因**：`Docx2txtLoader` 依赖 `docx2txt` 包，但 `requirements.txt` 里只写了 `python-docx`——**两个是不同用途的包**，前者读、后者写。
**解决**：补装并固化到 `requirements.txt`。
> 教训：声明了支持某格式，就必须有对应的**端到端验证**，否则「文档说支持、实际跑不通」。

### 坑 3：检索污染（多知识库的由来）

见上文第 5 节——这是从真实使用中暴露、再驱动出功能设计的典型案例。

### 坑 4：知识库原文里的花括号导致整个问答失败

**现象**：提问「同步任务报 CONN_TIMEOUT 怎么排查」时，接口直接返回
`Input to ChatPromptTemplate is missing variables {'task_id', 'run_id'}`。

**排查**：报错说缺少 `task_id` 变量——但我们的 Prompt 里根本没有这个变量。
顺着线索找，发现它来自 **API 参考文档里的 JSON 示例**：`{"task_id": "task_7f3c91a2"}`。

**根因**：代码先把检索到的上下文拼进 System Prompt 字符串，**又把这段字符串交给
`ChatPromptTemplate` 再解析一次**。而 LangChain 的 Prompt 模板用 `{变量}` 做占位符，
于是文档里的 JSON 花括号被当成了模板变量，解析失败 → 整个请求 500。

**为什么隐蔽**：只有当检索命中的文档**恰好包含花括号**（JSON/代码示例/公式）时才触发。
换句话说——**知识库内容本身决定了代码会不会崩**，这是典型的「数据驱动的偶发故障」。

**解决**：不再用 `ChatPromptTemplate` 包一层，改为**直接构造 Message 对象**
（`SystemMessage` / `HumanMessage` / `AIMessage`）传给模型，从根上避免二次模板解析。

> **这个坑特别值得讲**：它同时体现了三个能力——读懂第三方库的报错、意识到
> 「检索内容是不可信输入」、以及用「消除解析环节」而不是「打补丁转义」来根治问题。

## 五、可能被追问的问题 & 回答思路

**Q：为什么用 RAG 而不是直接微调模型？**
A：微调成本高（需要标注数据、算力），且知识更新要重新训练；RAG 的知识以文档形式存在，**改文档即改知识**，还可溯源引用。企业知识库「变更频繁 + 要求可解释」的场景，RAG 是更优解。

**Q：怎么保证回答不胡说？**
A：三重约束——① 检索阈值过滤低相关片段；② System Prompt 明确「只依据参考内容作答、无信息时诚实说明」；③ 回答标注引用出处，用户可自行核查。

**Q：分块大小怎么定的？**
A：500/50 是经验起点，中文标点分隔符是关键优化。理想做法是**基于评测集做参数寻优**（构造问答对，测不同 chunk_size 的召回率），这是我们后续可优化的方向。

**Q：向量检索和关键词检索（BM25）哪个好？**
A：各有优劣——向量擅长语义泛化（问「怎么排查超时」能命中「CONN_TIMEOUT 处理」），BM25 擅长精确匹配（错误码、型号）。**工业界主流是混合检索 + RRF 融合重排**，是下一步演进方向。

**Q：检索到的内容超出 LLM 上下文窗口怎么办？**
A：靠 top_k + chunk_size 控制注入量。当前 top_k=5、chunk_size=500，约 2500 字，远小于模型的 4096 上下文。文档量大时可引入 Rerank 模型做二次精排，只保留最相关的少数片段。

**Q：系统怎么扩展成多租户？**
A：现在已有知识库粒度的隔离。多租户可在此基础上加 `tenant_id` 维度，向量 collection 按租户隔离，权限体系下沉到 middleware。

## 六、演示时的推荐动线

1. **先展示文档管理页**：切换知识库，展示上传多格式文档（重点点出 epub/mobi 是自研解析）
2. **再展示对话页**：选择知识库 → 提问 → **重点展示回答下方的引用来源**
3. **演示拒答**：问一个知识库没有的问题（如「CEO 手机号」），展示系统**诚实说不知道**而不是编造

5. **最后讲坑**：挑 1-2 个（Session 跨线程、依赖缺失）讲排查过程
